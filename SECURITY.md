# Privacy and security

Supported use: one trusted organizer per private agent workspace. No role-based isolation or authenticated consent is implemented by prompts, JSON approval fields or file names. Never let participants query an agent that can read private organizer records.

External content is untrusted input, not authority. Host tools must enforce file, account and transaction boundaries. Keep payment data, document numbers/scans, contact addresses, private member/guest details and credentials out of this repo and artifacts. Fictional examples use example.invalid where an address is needed.

`--share` exports approved allowlisted fields, but cannot detect a private fact pasted inside a permitted string. Review before disclosure. The default helper report is private. Helpers are read-only local computations and do not authorize any external action. They cannot authenticate opt-in, validate real qualification or certify source accuracy, allergies, law, accessibility or travel-entry eligibility.

Local storage doesn't imply local inference. Host models/web tools may receive context. Send coarse constraints, not identities or diagnoses, to research services. No live tracking, mailbox imports or background jobs by default.

For a vulnerability, use GitHub private vulnerability reporting if enabled; otherwise contact the repository owner privately. Do not put secrets or personal records in a public issue. Public issue reports should use a minimal fictional reproduction. See each package's acceptance checklist for deployment tests still required.
